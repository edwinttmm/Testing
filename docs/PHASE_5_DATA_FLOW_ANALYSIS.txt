================================================================================
  LIFECYCLE EVENT HANDLING COMPARISON
================================================================================

EVENT: Frontend emits video_started(video_id="video_2", timestamp=12.0)

─────────────────────────────────────────────────────────────────
CURRENT (BROKEN):
─────────────────────────────────────────────────────────────────
  1. SocketIO receives event
  2. VideoSequenceOrchestrator.notify_video_started()
  3. Update sequence_metadata.current_video_id = "video_2"
  4. Update SequenceVideoResult.video_start_time = 12.0

  PROBLEM: If step 3 fails, metadata stays stale!
           Detection service only checks metadata (step 3)
           Never queries SequenceVideoResult (step 4)

─────────────────────────────────────────────────────────────────
PHASE 5 (PROPOSED):
─────────────────────────────────────────────────────────────────
  1. SocketIO receives event
  2. HTTP POST to Unified Service
  3. Service updates in-memory cache
  4. Service write-through to sequence_metadata
  5. Service write-through to SequenceVideoResult
  6. Service broadcast to SocketIO

  PROBLEM: More steps = more failure points!
           If step 2 (HTTP) fails, entire chain fails
           If service crashes, cache lost
           Still relies on event being emitted!

─────────────────────────────────────────────────────────────────
PHASE 4 (RECOMMENDED):
─────────────────────────────────────────────────────────────────
  1. SocketIO receives event
  2. VideoLifecycleCoordinator.video_started()
       - Idempotent: Check if already recorded
       - Write to SequenceVideoResult ONLY
       - ATOMIC: Single DB write

  3. Detection occurs later (timestamp=15.5)
  4. VideoAssignmentService queries SequenceVideoResult
       - Finds video_2 (start=12.0, end=NULL)
       - Returns video_2

  BENEFITS:
    ✅ Fewer steps = fewer failure points
    ✅ Idempotent: Duplicate events handled gracefully
    ✅ ATOMIC: Single DB write (ACID guarantees)
    ✅ Detection assignment WORKS even if event fails!
       (Because timestamp query works with partial data)

  EXAMPLE: What if video_started event never emitted?
    - SequenceVideoResult has: video_1 (0-12), video_2 (NULL-NULL)
    - Detection at 15.5s queries: Finds video_2 (last video, no end)
    - STILL WORKS! (with reduced confidence, emits warning)

================================================================================
  PERFORMANCE TRACE
================================================================================

Scenario: 30 detections/second during multi-video test

─────────────────────────────────────────────────────────────────
CURRENT (BROKEN):
─────────────────────────────────────────────────────────────────
  Per Detection:
    1. Read session from DB:          3ms
    2. Parse JSON sequence_metadata:  <1ms
    3. Extract current_video_id:      <1ms
  
  Total: ~4ms per detection (fast but WRONG!)

─────────────────────────────────────────────────────────────────
PHASE 5 (PROPOSED):
─────────────────────────────────────────────────────────────────
  Per Detection:
    1. HTTP request to service:       5-10ms
    2. Service reads cache:           <1ms
    3. Cache miss? Query DB:          3-5ms (occasional)
    4. HTTP response:                 5-10ms
  
  Total: 10-25ms per detection (slow and still may be wrong!)
  
  At 30 Hz:
    30 detections × 15ms = 450ms CPU/sec
    Overhead: +300% vs current

─────────────────────────────────────────────────────────────────
PHASE 4 (RECOMMENDED):
─────────────────────────────────────────────────────────────────
  Per Detection:
    1. Direct SQL query (indexed):    2-5ms
    2. Return video_id:               <1ms
  
  Total: 3-6ms per detection (fast and CORRECT!)
  
  At 30 Hz:
    30 detections × 4ms = 120ms CPU/sec
    Overhead: +5% vs current

  BONUS: Query result can be cached if needed
         (but usually not necessary due to fast query)
