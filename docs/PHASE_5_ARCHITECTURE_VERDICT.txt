   Current:  3 sources (sequence_metadata, SequenceVideoResult, SocketIO)

   Phase 4:  1 source (SequenceVideoResult - immutable database)

2. DOES NOT SOLVE ROOT CAUSE

   Root Cause: Architecture relies on event-driven state updates from
               unreliable source (frontend video player events)

   Phase 5:    Still requires notify_video_started() events to work
               Just adds caching layer on top of broken event system

   Phase 4:    Eliminates reliance on events entirely
               Computes video_id from immutable timing records

   Verdict: Only Phase 4 fixes root cause

3. PERFORMANCE REGRESSION

   Current:    Read JSON field = 1ms (but wrong!)
   Phase 5:    HTTP → Service → Cache → DB = 10-25ms per detection
               At 30 Hz: 450ms CPU/sec = 300% overhead

   Phase 4:    Direct SQL query = 2-5ms per detection
               At 30 Hz: 120ms CPU/sec = 5% overhead

   Verdict: Phase 4 is 4x faster

4. MIGRATION DATA LOSS RISK

   Phase 5:    Must migrate state from 3 inconsistent sources → 1
               Problem: Which source is authoritative?
                 - sequence_metadata may be stale
                 - SequenceVideoResult incomplete
                 - SocketIO cache lost on restart
               Risk: HIGH data loss or corrupt state

   Phase 4:    No migration needed
               Use existing SequenceVideoResult (already correct)
               Risk: ZERO data loss

   Verdict: Phase 4 is infinitely safer

5. SINGLE POINT OF FAILURE

   Phase 5:    Unified Service must handle:
                 - All video lifecycle events
                 - All detection queries (30/sec)
                 - All timing synchronization
                 - Cache invalidation
               IF service crashes → Entire HIL system stops

   Phase 4:    Detection service queries database directly
               IF query fails → Database has replicas/failover
               No single service dependency

   Verdict: Phase 4 is resilient, Phase 5 is fragile

6. OVER-ENGINEERING

   Problem Size:     ~100 LOC across 3 files causing bugs

   Phase 5 Solution: 1,350 LOC + new service + Redis + 5 APIs
   Ratio:            13.5x over-engineered

# Detection assignment with timestamp-based lookup
from services.detection_video_assignment import get_video_assignment_service

def _store_event_in_db(event: DetectionEvent, db: Session):
    # STEP 1: Compute video_id from timestamp (AUTHORITATIVE)
    assignment_service = get_video_assignment_service()
    assignment = assignment_service.get_video_for_timestamp(
        session_id=event.session_id,
        detection_timestamp=event.timestamp,
        db=db
    )

    video_id = assignment.video_id  # ✅ ALWAYS CORRECT

    # STEP 2: Cross-validate with metadata (ADVISORY ONLY)
    metadata_video_id = get_metadata_video_id(event.session_id, db)

    if metadata_video_id != video_id:
        # ⚠️ DRIFT DETECTED - Alert but trust timestamp
        logger.warning(f"Metadata drift: {video_id} vs {metadata_video_id}")
        emit_alert("metadata_drift", {...})

    # STEP 3: Store with correct video_id
    event.video_id = video_id
    db.add(event)
