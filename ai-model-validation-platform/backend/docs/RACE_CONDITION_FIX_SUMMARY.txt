🔴 PROBLEM IDENTIFIED
─────────────────────────────────────────────────────────────────────
Multiple videos can start simultaneously in multi-video sequences.
The sequence_start_time field had NO database-level locking.

Race Condition Pattern:
  Thread A: Read start_time=NULL → Set 100.0 → Commit
  Thread B: Read start_time=NULL → Set 100.5 → Commit ← OVERWRITES!

Result: Non-deterministic timing, last write wins

🟢 SOLUTION IMPLEMENTED
─────────────────────────────────────────────────────────────────────
Atomic Compare-And-Swap (CAS) with SELECT FOR UPDATE locking

New Method: _initialize_sequence_start_atomic()
  - Locks database row with SELECT FOR UPDATE
  - Atomic check: if start_time is NULL, set it
  - Returns True/False based on CAS success
  - Retry logic with exponential backoff (3 attempts)

Fixed Pattern:
  Thread A: LOCK → Check NULL → Set 100.0 → Commit → UNLOCK
  Thread B: WAIT → LOCK → Check NOT NULL → Rollback → Use 100.0

def _initialize_sequence_start_atomic(
    self,
    db: Session,
    sequence_id: str,
    start_time: float
) -> bool:
    """
    Atomically initialize sequence_start_time using CAS pattern.
    Uses SELECT FOR UPDATE to lock the row at database level.
    """
    max_retries = 3
    retry_delay = 0.01  # 10ms

    for attempt in range(max_retries):
        try:
            # 🔒 CRITICAL: Lock the row
            stmt = select(VideoTestSequenceModel).where(
                VideoTestSequenceModel.id == sequence_id
            ).with_for_update()

            video_sequence_db = db.execute(stmt).scalar_one_or_none()

            # ⚛️ Atomic check-and-set
            if video_sequence_db.sequence_start_time is None:
                video_sequence_db.sequence_start_time = start_time
                video_sequence_db.status = "running"
                db.commit()  # ✅ Release lock
                return True  # Won the race
            else:
                db.rollback()  # ✅ Release lock
                return False  # Lost the race

        except SQLAlchemyError as e:
            db.rollback()
            time.sleep(retry_delay)
            retry_delay *= 2  # Exponential backoff

    return False

🔍 HOW CAS PREVENTS RACE CONDITIONS
─────────────────────────────────────────────────────────────────────

1. SELECT FOR UPDATE creates exclusive lock on database row
2. Only ONE thread can read/modify the locked row
3. Other threads BLOCK until lock is released
4. Check and set are ATOMIC - no race window

Timing Diagram:
  T0: Thread A locks row  🔒
  T1: Thread B tries lock → BLOCKS ⏸️
  T2: Thread A sets value → commits → unlocks 🔓
  T3: Thread B acquires lock 🔒
  T4: Thread B sees value already set → rollback → use existing 🔓

Result: Exactly ONE thread sets the value, all others reuse it
