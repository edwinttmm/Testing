# Ground Truth Matching Analysis: PRD vs Implementation

## Executive Summary

**Current Issue**: System shows 100% frame alignment but 0% ground truth matching, indicating a fundamental disconnect between the INTENDED ground truth matching logic (as defined in PRD) and the ACTUAL implementation.

## PRD Requirements (Product Requirements Document)

### Module 4: Analysis & Reporting (PRD Lines 126-148)

#### 4.1 Automated Performance Analysis

The PRD defines THREE distinct detection outcomes:

1. **Pass (True Positive)**
   - A hardware signal is received AND
   - The calculated latency is WITHIN the user-defined threshold
   - Formula: `Latency = Signal_Received_Time - Expected_Event_Time`

2. **Fail (High Latency)**
   - A signal IS received BUT
   - The latency EXCEEDS the threshold

3. **Fail (Missed Detection/False Negative)**
   - NO signal is received within a reasonable window of an expected event

#### Key PRD Variables & Timing:

```
Test_Start_Time:       Exact moment video playback begins (Time 0 reference)
Expected_Event_Time:   Calculated for every annotated event, relative to Test_Start_Time
Signal_Received_Time:  Instant LabJack receives high signal from camera
Latency:              Signal_Received_Time - Expected_Event_Time
```

#### PRD Requirements Summary:
- **Precision timing**: Sub-millisecond precision using monotonic clock
- **Temporal matching**: Events matched by timing windows, not frame numbers
- **User-defined threshold**: Maximum acceptable latency in milliseconds
- **Ground truth source**: Pre-validated annotations (bounding boxes) from video
- **Detection source**: LabJack TTL signals indicating camera hardware detection

## Actual Implementation: Ground Truth Matching Service

### From `/backend/services/ground_truth_matching_service.py`

#### Algorithm Overview:

```python
def _perform_temporal_matching(detections, ground_truth, tolerance_ms):
    """
    Phase 1: Match ground truth to detections (True Positives)
    - For each ground truth object:
      - Find closest detection within tolerance window
      - Use first-match strategy
      - Calculate temporal offset and latency

    Phase 2: Mark remaining detections as False Positives
    - Any detection not matched to ground truth = FP

    Phase 3: Mark unmatched ground truth as False Negatives
    - Any ground truth without matching detection = FN
    """
```

#### Matching Criteria:

**True Positive (TP)**:
```python
time_diff = abs(detection.timestamp - gt_obj.timestamp)
if time_diff <= tolerance_seconds:  # Default: 100ms = 0.1s
    # Match found!
    temporal_offset_ms = (detection_time - gt_time) * 1000
    latency_ms = temporal_offset_ms if temporal_offset_ms >= 0 else None
    iou_score = 1.0 - (time_diff / tolerance) * 0.5
```

**False Positive (FP)**:
- Detection event with NO ground truth within tolerance window

**False Negative (FN)**:
- Ground truth object with NO detection within tolerance window

Given 24 ground truth objects and ~22 LabJack detections:

## Root Cause Analysis: Why 0% Ground Truth Matching?

### Hypothesis 1: Missing Ground Truth Data ⚠️

**Check**:
```sql
SELECT COUNT(*) FROM ground_truth_objects WHERE video_id = ?
```
- If returns 0: Ground truth not loaded for this video
- Expected: 24 rows

**Symptom**: All detections classified as False Positives (no ground truth to match)

### Hypothesis 2: Timestamp Misalignment ⚠️⚠️

**Critical Issue**: `video_relative_timestamp` not populated correctly

```python
# In matching service (line 256-259):
detection_time = (
    detection.video_relative_timestamp  # Could be NULL!
    if getattr(detection, "video_relative_timestamp", None) is not None
    else detection.timestamp  # System time != video time
)
```

**Problem**: If `video_relative_timestamp` is NULL or incorrect:
- Uses system `timestamp` instead (e.g., 1735494123.456)
- Ground truth uses video time (e.g., 1.042s)
- Comparison: abs(1735494123.456 - 1.042) = HUGE number
- Result: NEVER within 100ms tolerance window
- Outcome: 0% matches, all False Positives

**Verification**:
```sql
SELECT
    id,
    timestamp,
    video_relative_timestamp,
    CASE
        WHEN video_relative_timestamp IS NULL THEN 'MISSING'
        WHEN video_relative_timestamp < 0 THEN 'NEGATIVE'
        WHEN video_relative_timestamp > 10 THEN 'TOO_LARGE'
        ELSE 'OK'
    END as status
FROM detection_events
WHERE test_session_id = 'current_session';
```

### Hypothesis 3: Wrong Video Reference ⚠️

**Check**:
```sql
SELECT

### Hypothesis 4: Tolerance Window Too Small

**Check**:

```

If tolerance < 10ms and actual system jitter > 10ms, no matches possible.

Default: 100ms (should be sufficient)

## Conclusion

The PRD clearly defines ground truth matching as a **temporal correlation** between:
- **Ground Truth**: Pre-validated detection events at specific video timestamps
- **Detection Events**: LabJack-captured signals with video-relative timestamps
- **Matching Logic**: Temporal proximity within tolerance window (±100ms)

The implementation (`ground_truth_matching_service.py`) correctly implements this algorithm, BUT the issue is likely:

1. **Missing ground truth data** for the test video, OR
2. **Missing/incorrect `video_relative_timestamp`** in detection events, OR
3. **Wrong video ID** linking sessions to ground truth

The 100% frame alignment confirms the video playback and detection capture is working. The 0% ground truth matching indicates the temporal comparison is failing due to missing or misaligned timestamp data.

**Next Step**: Run diagnostic queries to identify which of the three issues is causing the problem.
